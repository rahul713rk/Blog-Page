BUG #2 — XSS VULNERABILITY IN SEARCH RESULTS
--------------------------------------------------------------------------------
File: assets/js/search.js (lines 27-32)

PROBLEM:
  Search results render doc.url and doc.title directly into innerHTML without
  any sanitization. If a post URL or title contains HTML characters or
  malicious script tags, this will inject arbitrary HTML into the page.
  
  Vulnerable code:
    return `<article>
      <h3><a href="${doc.url}">${doc.title}</a></h3>
      <p>${doc.description}</p>
    </article>`;

  Although the search index is build-time generated, this is still a bad practice
  and an attack surface if the build pipeline is ever compromised.

FIX:
  Add a simple escapeHtml helper and use it for all dynamic values:

    function escapeHtml(text) {
      return String(text || "")
        .replace(/&/g, "&amp;")
        .replace(/</g, "&lt;")
        .replace(/>/g, "&gt;")
        .replace(/"/g, "&quot;")
        .replace(/'/g, "&#39;");
    }

  Then in the template:
    return `<article>
      <h3><a href="${escapeHtml(doc.url)}">${escapeHtml(doc.title)}</a></h3>
      <p>${escapeHtml(doc.description)}</p>
    </article>`;

BUG #3 — SEARCH.JS HAS NO ERROR HANDLING FOR THE FETCH CALL
--------------------------------------------------------------------------------
File: assets/js/search.js (lines 10-11)

PROBLEM:
  The fetch for search-index.json and the subsequent .json() parse have no
  try/catch or .catch() handler. If the network request fails (e.g. on a cold
  GitHub Pages load, or if the user is offline), the unhandled promise rejection
  will silently break the entire search feature with no user feedback.

  Vulnerable code:
    const response = await fetch(`${sitePath}/search-index.json`);
    const payload = await response.json();

FIX:
  Wrap the async setup body in a try/catch:

    async function setupSearch() {
      const input = document.querySelector("#search-input");
      const results = document.querySelector("#search-results");
      const sitePath = document.body?.dataset.sitePath || "";
      if (!input || !results || typeof lunr === "undefined") return;

      let index, documents;
      try {
        const response = await fetch(`${sitePath}/search-index.json`);
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const payload = await response.json();
        index = lunr.Index.load(payload.index);
        documents = new Map(payload.documents.map((doc) => [doc.id, doc]));
      } catch (err) {
        results.innerHTML = "<p>Search is unavailable right now.</p>";
        return;
      }
      // ... rest of function
    }

BUG #4 — LUNR IS LOADED TWICE (PERFORMANCE & TIMING BUG)
--------------------------------------------------------------------------------
Files:
  - templates/layout.html (line 111)
  - package.json / build pipeline (lunr is a build-time dependency)

PROBLEM:
  lunr is installed as an npm package (used server-side in site-builder.js
  to build the search index at build time). It is ALSO loaded from a CDN at
  runtime in layout.html:
    <script src="https://cdn.jsdelivr.net/npm/lunr/lunr.min.js"></script>

  This means lunr is downloaded by every visitor's browser even on pages that
  have no search box (e.g. all post pages). It's a wasted ~8KB download per page.
  Additionally, search.js has `typeof lunr === "undefined"` as a guard —
  meaning if the CDN is slow, search silently fails.

FIX:
  Option A (Recommended): Move the lunr CDN <script> tag to only the index
  page. In page-renderer.js, add it to the `head` variable only for the
  index page (page 1), similar to how search.js is only included there.

  Option B: Remove the CDN entirely and bundle lunr into your own search.js
  using a bundler like esbuild or Rollup.

BUG #7 — COLLAPSIBLE HEADING IDs CAN COLLIDE (content-ui.js)
--------------------------------------------------------------------------------
File: assets/js/modules/content-ui.js (lines 120, 129)

PROBLEM:
  When building heading collapsibles, the aria-controls and content ID are
  generated like:
    button.setAttribute("aria-controls", `${heading.id || `section-${level}`}-content`);
    content.id = `${heading.id || `section-${level}`}-content`;

  If a heading has no id, multiple H1s or H2s will all fall back to
  "section-1-content" or "section-2-content", creating duplicate IDs on the
  page. This breaks accessibility (ARIA) and browser anchor behavior.

FIX:
  Use a running counter:
    let headingCounter = 0;
    // inside forEach:
    const safeId = heading.id || `section-${level}-${++headingCounter}`;
    button.setAttribute("aria-controls", `${safeId}-content`);
    content.id = `${safeId}-content`;
